# BookFlow review — 9 October 2026

## Conclusion

The core booking flow works in the local verification performed today. This is
a project MVP, not a certification that every feature or production scenario is
correct. The recurring maintenance failure was associated with an unavailable
local database; it disappeared after Docker/PostgreSQL were started and the
database was initialized.

## Scope examined

- Active React routes, planner, booking actions, account state, owner settings,
  and seat-pool UI; HTTP helper and Vite proxy.
- Express routing, validation, account authorization and tenant checks.
- Availability SQL, resource locks, transaction helper, holds, expiry,
  rescheduling, cancellation, waitlist promotion, and background maintenance.
- Seat-pool publication, allocation, confirmation, withdrawal and solver.
- Baseline schema and migrations, database connection setup, account links,
  notifications, CSV export, rate limits, Docker build and backup scripts.
- Existing integration suite. Legacy unmounted features were distinguished from
  the active application; they were not individually exercised as live products.

## Observed failure and repairs

1. PostgreSQL at localhost:54329 refused connections. Docker Desktop was stopped.
   Started Docker Desktop and the Compose database, applied migrations 000–008,
   and seeded the newly created local database. No existing database records
   were reset or removed.
2. Maintenance previously discarded its error details. It now logs the error
   code and message, making future failures diagnosable.
3. Maintenance could leak its checked-out connection if leadership unlock
   failed. Connection release now runs in a nested finally block; a failed
   connection is removed from the pool.
4. A one-connection pool could stall maintenance because it holds a leadership
   connection while tasks borrow another. Configuration now rejects
   DB_POOL_MAX=1 when maintenance is enabled.
5. Backup fallback assumed a container named bookflow-postgres, but Compose
   created bookflow-db-1. The script now discovers the Compose db container and
   still supports an explicit BOOKFLOW_DB_CONTAINER override.
6. Added an integration test for successful maintenance and leadership release.

## Remaining issues and practical limitations

- Resource creation in client/src/flow/Settings.tsx sends slotStep: 15 as a
  literal. The backend supports other intervals, but the active UI does not let
  an owner choose or edit this interval. This contributes to confusion between
  fixed hourly slots and flexible start times; it is not an overlap bug.
- The baseline schema and older frontend/backend folders contain unused payment,
  review, coupon and other features. The schema after all migrations is the
  actual active data model. These files make learning and maintenance harder.
- Rejoining a cancelled seat request reuses its request ID. Seat-offer notices
  deduplicate only by that ID, so a later offer can lack a fresh notification.
  This path does not yet have regression coverage.
- Seat-request cancellation commits before a subsequent reallocation. If the
  solver hits its search limit, the endpoint can return an error even though
  cancellation succeeded. The frontend refreshes after errors, but the response
  semantics should be improved.
- Chat interprets relative dates using the first organization's timezone before
  catalog verification. Different-timezone businesses need a clearly selected
  context for relative words such as tomorrow.
- Polling updates some pages every 15 seconds; there is no WebSocket layer.
- Catalog reads have no pagination, and settings use per-resource queries.
  Large catalogs and sustained traffic have not been load-tested.
- Complete interactive browser journeys, mobile/accessibility checks, Docker
  image runtime validation, cloud deployment, live SMTP/Gemini reliability,
  and production backup/restore have not been verified in this review.

## Starting locally after stopping Docker

Open Docker Desktop, run docker compose up -d db, then npm run dev. The database
is already initialized; db:setup includes demo seeding and should not be rerun
against a populated business database. Use npm run db:migrate for future schema
updates. If maintenance fails again, inspect the new error code/message and
/api/health before assuming the booking algorithm is broken.
